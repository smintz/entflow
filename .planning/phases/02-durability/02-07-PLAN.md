<objective>
Give the worker a lifecycle: a poll loop that does not stampede, a wakeup path
that does not replace polling, a shutdown that is honest about what it
guarantees, and two deployment topologies that are provably the same object.

D-49's framing is the plan's own acceptance test: **shutdown is a crash we
happened to be polite about.** If graceful shutdown needs any mechanism
crash-resume does not already provide, that is a signal the crash-resume story is
incomplete — so this plan should add remarkably little, and what it adds should
be about politeness, not correctness.

Purpose: DUR-09 and DUR-10, and the worked example plan 02-08 will kill.
Output: `worker/loop.go`, `Shutdown`, and `internal/testdata/crashworker`.
</objective>

  <files>worker/loop.go, worker/worker.go, worker/loop_test.go</files>
  <action>
    Move the loop out of `worker/worker.go` into `worker/loop.go` so the
    constructor file stays about construction and validation.

    Each claim goroutine waits `Options.PollInterval` adjusted by a random factor
    within plus-or-minus `Options.Jitter` on **every** wait, not once at startup.
    Jitter is mandatory, not tunable-to-zero-by-accident: the poll storm it
    prevents is a named performance trap, and N workers started by the same
    deployment at the same second will otherwise converge and stay converged.
    Document that reasoning in the doc comment so a future reader does not
    "simplify" it away.

    A goroutine that claims a run does not wait before its next iteration — work
    found means more work may be waiting, and a run needs one claim per step, so
    a multi-step run would otherwise take one poll interval per step. This is the
    single most impactful latency property in the loop; state it in the doc
    comment.

    Wire the nudge: each goroutine selects on its jittered timer, the engine's
    nudge channel, and its context's done channel. A nudge short-circuits the
    wait. The channel is buffered and the send is non-blocking, so a nudge is
    never a backpressure path and a slow worker can never stall `Start`. Polling
    remains the correctness backstop in every topology — a nudge that is missed,
    dropped, or that cannot cross a process boundary costs latency and nothing
    else. Cross-process wakeup is deliberately absent in Phase 2 and arrives with
    the transactional outbox work; say so in the doc comment rather than leaving
    a reader to wonder whether it was forgotten.

    Each iteration keeps its own recover boundary around its transaction
    bookkeeping, separate from the per-closure recover that already lives in
    `runStep`.

    Cover it in `worker/loop_test.go` against SQLite via `entclient`: successive
    waits differ, and over many samples all fall within the configured jitter
    band around the interval — assert the band, not an exact sequence, so the
    test is not flaky; a nudge delivered while a goroutine is waiting shortens
    that wait materially below the configured interval; a run started with the
    nudge channel deliberately drained still completes, proving polling is the
    backstop; and a goroutine that claims a run begins its next claim without
    waiting a full interval.
  </action>

    - A test asserts a nudge delivered during a wait causes the next claim attempt to occur materially sooner than one full poll interval.

  <files>worker/worker.go, worker/loop.go, worker/shutdown_test.go</files>
  <action>
    Implement `Shutdown(ctx context.Context) error` in three beats, and add
    nothing beyond them.

    First, stop claiming: signal every goroutine to finish its current iteration
    and start no new claim. Second, wait for in-flight step transactions to
    commit, bounded by `Options.DrainTimeout` or by the caller's own context
    deadline, whichever expires first. Third, past that deadline, cancel the
    step contexts so their transactions roll back, and return an error naming
    how many claims were still in flight when the deadline expired — a silent
    truncation here is the operator-facing lie this whole plan exists to avoid.

    The framing belongs in the doc comment verbatim, because it is what makes
    the guarantee obviously true rather than merely asserted: shutdown is a crash
    we happened to be polite about. A rolled-back step leaves the run exactly as
    claimable as it was, which is the same property a crash gives it. If any
    part of this implementation needs a mechanism crash-resume does not already
    provide — a drain table, an in-memory registry of claimed runs, a handoff
    protocol — stop and surface it, because that is evidence the crash-resume
    story has a hole, not evidence that shutdown needs more machinery.

    `Shutdown` must be safe to call twice and safe to call on a worker that was
    never started. It must not assume a single goroutine or a single worker
    process: it drains this process's pool and makes no claim about any other
    worker, consistent with the recorded decision that the unit of ownership is
    the run claim rather than the worker.

    `Run` returns cleanly when its own context is cancelled, taking the same
    path as `Shutdown` with a zero drain window, so a caller who only has a
    context does not get a different guarantee than one who calls `Shutdown`.

    Cover it in `worker/shutdown_test.go` against SQLite via `entclient`: a
    shutdown issued while a step is mid-flight returns only after that step's
    transaction has committed, and the effect is present; a shutdown whose drain
    deadline expires with a deliberately slow step returns a non-nil error
    naming the in-flight count, the step's transaction is rolled back, its effect
    is absent, the run's progress pointer is unadvanced, and a fresh worker
    claims and completes the run afterwards — the paired absence claim, exactly
    as a crash test would assert it; `Shutdown` called twice is a no-op the
    second time; `Shutdown` on an unstarted worker returns without error; and
    cancelling `Run`'s context produces the same run-state outcome as calling
    `Shutdown` with a zero drain window.
  </action>
  <verify>
    <automated>go build ./... && go vet ./... && go test ./worker/... -run 'TestShutdown' -count=1 -race</automated>
  </verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process termination signal → in-flight step transaction | the drain window is where politeness either holds or degrades to a crash |
| environment variables → the dedicated binary's database connection | an operator-supplied data source string reaches a driver |
| two independent worker processes → one shared run table | the only coordination point, and it is the database |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-17 | Denial of Service | synchronized poll storms from N workers deployed together | medium | mitigate | Jitter is applied to every wait, not once at startup, and is documented as the required mitigation rather than an optimization; a test asserts consecutive waits differ and lie within the configured band. A goroutine that claimed work does not wait at all, so throughput does not degrade to one step per interval. |
| T-02-18 | Denial of Service | a slow step holding a claim past the drain deadline and stalling shutdown | medium | mitigate | `DrainTimeout` bounds the wait; past it the step contexts are cancelled and their transactions roll back, leaving the run claimable. `Shutdown` returns a non-nil error naming the in-flight count rather than reporting a clean exit it did not achieve. |
| T-02-19 | Information Disclosure | a database data source string, including credentials, reaching logs or process listings from the dedicated binary | medium | mitigate | The binary reads the data source from an environment variable and must never echo it — not on startup, not in an error. The connection error path names the failure and the variable's name, never its value, following the discipline `codec.go` established for input bytes. |
| T-02-04 | Spoofing | the dedicated binary running with a standing privileged viewer | medium | mitigate | The binary supplies its viewer through the same application-owned `Options.Context` hook every in-process caller uses; the run entity's own `Policy()` decides what that viewer may do, and entflow ships no privileged default. |
| T-02-SC | Tampering | Go module dependencies | high | mitigate | This plan adds **no** new modules; the binary uses the Postgres driver already pinned in plan 02-03 and keeps it out of the non-test graph by living under `internal/testdata`, asserted by `TestNoTransportDeps`. RESEARCH.md's `## Package Legitimacy Audit` records no `[ASSUMED]`, `[SUS]` or `[SLOP]` package for this phase. |
