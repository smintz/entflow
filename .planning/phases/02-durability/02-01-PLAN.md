<objective>
Make a run a real row in a real table, and unlock the one mechanism the rest of
the phase is impossible without.

Phase 2's entire crash-safety story rests on D-30: the claim query and the step
mutation share one transaction. RESEARCH.md proved that is unreachable through a
plain generated ent client — `config.driver` is unexported, so nothing outside
the generated package can reach the raw connection a `*ent.Tx` wraps. Ent's
`sql/execquery` feature flag is the only supported unlock, and it must land
before any claim-loop code exists.

This plan is the phase's hard prerequisite plus the persistence substrate the
tracer (plan 02-02) writes into: the `sql/execquery` regeneration, `entflow.RunMixin()`,
`entflow.WithOwnerRef`, and the hand-written `CancelOrderFlowRun` fixture entity.

Purpose: without an execquery-enabled client there is no claim query; without a
run table there is no run.
Output: a regenerated fixture ent package carrying `ExecContext`/`QueryContext`,
`entflow.RunMixin()` / `entflow.WithOwnerRef`, and a migrated
`cancel_order_flow_runs` table with a lineage edge to `orders`.
</objective>

<user_story>
**As a** Go developer building an ent-backed application,
**I want to** have my flow's execution recorded as an ordinary ent row I can see in
my own database,
**so that** a workflow's progress is inspectable with the same tools I already use
for every other entity, and a crash cannot lose it.
</user_story>

  <context>
    These two decisions are a single one-way door. Everything after this task
    writes rows into the shape chosen here, and from Phase 5 onward codegen is
    contractually obliged to emit exactly this shape. Undoing it later is a data
    migration for every adopter plus a breaking change to generated output — not
    a refactor.

    Both decisions were selected by `--auto` during `/gsd-discuss-phase`; no
    human weighed them. This checkpoint is the first and cheapest moment a human
    can look at the actual column list and the actual stored strings before they
    become a database schema.

    What is being ratified:
    - Columns on `entflow.RunMixin()` (D-28): `state`, `input`, `current_step`,
      `attempt`, `last_error`, `results`, `retry_after`, `trace_context`,
      `created_at`, `updated_at`, `started_at`, `finished_at` — plus `self_was`,
      which D-28's list omits but D-42 requires (the `SelfWas` entry snapshot
      must persist on the row rather than live in memory). The owner edge is the
      concrete schema's job, never the mixin's.
    - Stored `state` values (D-27): `pending`, `running`, `done`, `cancelled`,
      and one `failed:&lt;step&gt;` value per step in the flow's step graph, written
      with a literal colon via `field.Enum(...).NamedValues(...)`. RESEARCH.md
      verified against ent's own `entc/gen/type.go` that ent validates the Go
      identifier, never the stored value, so the colon is legal; and that ent's
      Postgres codegen emits a CHECK-constrained string column rather than a
      native `ENUM`, so adding a step later is not an `ALTER TYPE`.
  </context>
  <options>
    <option id="ratify-as-specified">
      <name>Ratify D-23 and D-27 exactly as CONTEXT.md specifies (recommended)</name>
      <pros>Matches the design document's §3.5 verbatim; `failed:refund` is literally what an operator sees in a SQL query, so the Phase 5 claim that the enum is derived from the step graph has real content; the mixin is what keeps the hand-written and generated run entities the same artifact.</pros>
      <cons>Locks thirteen column names and a colon-bearing enum vocabulary into every adopter's database.</cons>
    </option>

      <name>Ship a fixed five-value enum (`pending`/`running`/`done`/`cancelled`/`failed`) with the failing step in `current_step`</name>
