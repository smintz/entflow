<objective>
Make a run observable end to end, including across the boundary where it stops
being one process.

A durable run's steps may execute in different processes after a crash or a
re-claim. Ambient context propagation cannot survive that — which is invisible
until someone opens a trace for a crashed run and finds two unrelated traces.
D-59 fixes it by persisting the trace context on the run row and restoring it as
the parent at each claim.

This plan also settles the one decision CONTEXT.md flagged as most worth a second
look: how wide entflow's OpenTelemetry dependency actually is. RESEARCH.md
measured it — the trace API alone resolves to zero external modules, while the
ambient global convenience API pulls in five more. **Decision recorded here,
resolving RESEARCH.md open question 1: the tracer provider defaults to the
no-op provider from the trace module itself, never to the ambient global.**
An application that wants entflow's spans in its own pipeline passes its provider
explicitly through `worker.Options`. This keeps D-57's exception genuinely narrow
rather than accidentally wide, and the narrowness is asserted mechanically.

Purpose: OPS-05, and an honest dependency boundary.
Output: `worker/span.go`, per-step spans, cross-process trace continuity, and an
amended-but-still-derived META-02 gate.
</objective>

<user_story>
**As a** developer debugging a workflow that failed in production,
**I want to** open one trace and see the whole run — every step, its attempt
count, and where it stopped — even though a crash moved it between processes,
**so that** a durable workflow is not a blind spot in the observability I already
have.
</user_story>

    Wire the spans into the claim path so the trace matches the run.

    On the first claim of a run — the one where `started_at` is set — start the
    run's root span, capture its span context, and persist it through that
    claim's advance write so every later claim, in any process, finds it. The
    root span is started and ended within that first claim; later claims restore
    it as a remote parent rather than holding a live span across a process
    boundary, which is not something a span can do. Say that in the doc comment,
    because a reader expecting a long-lived root span will look for one.

    On every claim that executes a step, restore the parent, start a child span
    named through Task 1's helper, set the run ID, flow, step, attempt and state
    attributes, and end it when the step's outcome is known. On a step error,
    record the error on the span through the error-recording API and set the
    span status to error; record the `StepError`'s rendered message, which names
    the step and kind and carries no input bytes. On the advance that reaches a
    terminal state, set the final state as an attribute.

    A claim cycle that finds nothing claimable starts no span at all — an empty
    poll is not a run event, and emitting one would flood a trace backend with
    noise proportional to the poll rate rather than to the work.

    A run whose every step is skipped by a false condition still gets its root
    span and zero child spans: the run happened, no step did.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| run row contents → span attributes | observability output escapes the run entity's row-level `Policy()` entirely |
| persisted trace context → a restored parent span | an attacker-controllable stored string is parsed into a trace identity |
| new module → entflow's production dependency graph | the META-02 contract boundary, deliberately amended here |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-03 | Information Disclosure | span attributes, span events, and error text emitted from the claim path | high | mitigate | Attributes are restricted to run ID, flow, step, attempt and state; error text comes from `StepError`'s rendered message, which never embeds input bytes. A test asserts no attribute value contains the run's input or any recorded step result. This is also the plan's prohibition. Field-level redaction of application data remains out of scope and is documented as a boundary. |
| T-02-15 | Spoofing | a forged or corrupted persisted trace context linking a run into an unrelated trace | low | accept | The stored value is written only by the worker's own advance write, which is already guarded and privacy-governed; a malformed value decodes to "no parent" rather than an error, so the worst outcome is a run that traces as its own root. Trace identity carries no authorization meaning anywhere in entflow. |
| T-02-11 | Elevation of Privilege | the D-57 exception silently widening beyond the tracing API | high | mitigate | The tracer provider defaults to the trace module's own no-op provider rather than the ambient global; the allowlist is derived from the packages entflow actually imports rather than a prefix exemption; and `TestTracingDependencyNarrowness` fails on any of the five modules the global path would introduce, and on the SDK. |
| T-02-16 | Denial of Service | span-name cardinality explosion from interpolated identifiers | medium | mitigate | The name is produced by one helper as the literal prefix plus flow and step; identifiers are attributes only.
