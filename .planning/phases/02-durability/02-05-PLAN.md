<objective>
Make a run an ops surface rather than an internal record: queryable with the
developer's own generated client, governed by an ordinary `Policy()`, and
cancellable by an operator — plus the privilege boundary that makes all three
safe.

OPS-01 requires no entflow code at all. That is the point: a run is an ordinary
ent entity, so "this order's runs" is a generated query and "who may see it" is a
`Policy()` the application writes. This plan proves that by using it, not by
building an access layer over it.

Purpose: the run row is the audit log and the control surface; the workflow
marker is what keeps privileged transitions from being forgeable.
Output: `internal/wfmarker` + `entflow.IsWorkflow`, the fixture's `Policy()`,
cancellation as a guarded transition, and the OPS-01 query proof.
</objective>

<user_story>
**As an** operator on call,
**I want to** find a customer's stuck workflow with the same query tooling I use
for every other row, see why it stopped, and cancel it,
**so that** an incident does not require a new dashboard, a new API, or a
developer.
</user_story>

  <action>
    Implement cancellation as a state transition, never a signal (D-43).

    `RunStore.Cancel` issues a conditional update setting the state to the
    cancelled value and `finished_at` to now, predicated on the run currently
    being in the pending or running state, and reports whether a row matched. A
    run already in any terminal state — cancelled, done, or any `failed:<step>`
    — matches nothing, so a second cancel changes nothing and reports the guard
    miss rather than erroring. That is what makes cancelling twice safe.

    No stop signal exists and none is needed: every terminal value is absent
    from the claim predicate's state list, so a cancelled run is structurally
    unclaimable from the moment the cancel commits. Do not add a check anywhere
    in the worker for "has this been cancelled" — if such a check appears, the
    claim predicate is wrong.

    Because the claim transaction holds the run's row lock for the whole step
    (D-30), a cancel issued mid-step blocks until that step commits and then
    applies. The in-flight step is allowed to finish. Cancellation means "no
    further steps", not "abort mid-step", and both the doc comment on `Cancel`
    and the operator-facing prose must say exactly that, because an operator who
    expects an immediate abort will file a bug against correct behavior.

    Add a small package-level helper on the engine so an application can cancel
    without hand-writing the transaction dance — resolving the store for a flow
    name, opening a transaction, calling `Cancel`, and committing — returning
    whether the run was actually cancelled. It must run under the caller's own
    context and viewer, never the worker's, so the run entity's `Policy()`
    governs it.

    Prove OPS-01 by using it rather than building it. In `ops_test.go`, query
    runs through the generated client with the fixture viewer in context: every
    run belonging to one order, traversed through the owner edge with the
    generated predicate package; runs filtered to a terminal failure state;
    runs ordered by creation time. Assert the results and assert that no
    entflow-specific query helper was needed — the test's own imports are the
    evidence, and its doc comment must say that this test exists to demonstrate
    the absence of a bespoke query layer.

    In `cancel_test.go`, against SQLite via `entclient`: cancelling a pending
    run moves it to the cancelled state and it is never claimed afterwards;
    cancelling the same run again reports no match and leaves the stored state
    and `finished_at` unchanged; cancelling a done run reports no match;
    cancelling while a step is in flight — the cancel goroutine blocking on the
    claim transaction's lock — results in the step's effect being committed, the
    run reaching the cancelled state, and no further step ever executing.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator context → run entity mutation | an authenticated but possibly unauthorized subject attempts a cancel |
| application viewer hook → worker context | the application supplies the privileged context the worker runs under |
| any caller → the workflow marker | the privilege signal that distinguishes a worker write from an ordinary one |
| ops query → run row contents | serialized input and results become visible to whoever passes the policy |
