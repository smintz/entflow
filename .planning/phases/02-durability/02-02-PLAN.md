inside one transaction, committed, and asserted from a test.

change to the shape proven here.

<task type="checkpoint:decision" gate="blocking">
  <decision>D-30: ratify that the claim transaction IS the step transaction — one transaction per claim, one step per transaction, no lease</decision>
  <context>
    This is the load-bearing decision of the phase and a one-way door: every
    crash-safety claim entflow makes, the whole crash-simulation release gate,
    and the absence of any lease machinery are all written against it. Undoing
    it later does not mean editing a function — it means reintroducing leases,
    reclaim predicates, and heartbeat columns into a published run-row schema,
    and rewriting every harness assertion.

    The shape being ratified: open one transaction; run the claim query
    (`... ORDER BY id LIMIT 1` with dialect-appropriate mutual exclusion);
    hydrate the claimed run through the generated client on that same
    transaction; execute exactly one DB step's closure against it; write the
    step's effect and the run's progress pointer; commit. A crash anywhere in
    that window rolls the whole thing back, leaving the row exactly as claimable
    as it was. DUR-03 (effect and progress commit together), DUR-05 (crash
    resumes cleanly) and DUR-06 (re-claim per step boundary, no lease) fall out
    structurally rather than being enforced by discipline.

    The reason this deserves a human look: it holds a database row lock for the
    entire duration of a step closure. That is safe and correct while every step
    is a DB step (Phase 2's scope, since Activity and Emit steps still refuse to
    execute), and it stops being safe the moment Phase 3's Activities put a
    network call inside that window — which is precisely when ACT-04's lease
    arrives. This checkpoint is where a human confirms that trade rather than
    inheriting it from an `--auto` selection.
  </context>
  <options>
    <option id="ratify-single-transaction">
      <name>Ratify D-30 exactly as CONTEXT.md specifies (recommended)</name>
      <pros>No lease, no heartbeat, no zombie-run reaper, no lease-expiry tuning in v1; the atomicity guarantee is structural, so no ordering a future generated runner could get wrong would commit an effect without its progress record; the crash harness's absence-claim assertions become provable rather than aspirational.</pros>
      <cons>A row lock is held for the duration of a step closure; a pathologically slow DB step blocks nothing else but its own run, yet does hold a connection. Phase 3 must add a lease when Activities split claim from execution.</cons>
    </option>
    <option id="claim-then-execute">
      <name>Claim in a short transaction, then execute the step in a second transaction</name>
      <pros>Row locks are held only for the claim; a slow step never holds one.</pros>
      <cons>Reintroduces exactly the gap this project exists to close: a crash between the two transactions can commit an effect with no progress record, or strand a claimed run with no lease to reclaim it. Requires lease columns and a reaper in Phase 2 rather than Phase 3. Contradicts the locked decision and the core value statement.</cons>
    </option>
    <option id="batch-claim">
      <name>Claim N runs per transaction rather than one</name>
      <pros>Fewer round trips per poll cycle at high run volume.</pros>
      <cons>Holds row locks across the execution of unrelated runs' steps, so one slow run stalls every run claimed alongside it. D-31 rejects it; concurrency is supposed to come from N independent claim transactions, not batching.</cons>
    </option>
  </options>
  <resume-signal>Select: ratify-single-transaction, claim-then-execute, or batch-claim</resume-signal>
</task>

    **`worker/dbstep.go` — claim, execute one step, advance, commit (D-30).**
    Write the single function that is the phase's whole safety argument. It
    opens a transaction via `store.BeginTx`, defers a rollback that is a no-op
    after a successful commit, runs the claim strategy against the transaction
    (which satisfies `entflow.RawQuerier` thanks to the plan 02-01
    regeneration), and returns "nothing claimable" cleanly when no row comes
    back. On a claim it loads the run through the store on that same
    transaction, marks the context as workflow-originated, resolves the flow's
    `Runner`, computes the ordered step list, determines the next step as the
    one following the run's `current_step` in that order (or the first step when
    `current_step` is empty), and executes exactly that one step. It then
    advances the run in the same transaction: `current_step` to the executed
    step, `state` to running or, when the executed step was the last, to done
    with `finished_at` set; `started_at` set on the first advance. Both the
    step's effect and this advance write must be inside the one transaction, and
    the commit is the only place either becomes durable. When every remaining
    step's conditions evaluate false, the advance walks straight to the done
    state without invoking a closure and records no result. Use `RunInTx`'s
    two-recover-site discipline as the model: the per-step recover already lives
    in `runStep` and must not be merged with the transaction-level one.
