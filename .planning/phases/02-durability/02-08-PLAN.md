<objective>
The release gate. No public release without this passing, because trust in a
workflow engine is won or lost on crash-resume.

Everything before this plan asserted that a crash is safe. This plan proves it,
twice: once in-process at every logical boundary the step graph produces, and
once by actually terminating a real worker process against a real Postgres. The
assertions are absence claims, not terminal-state equality — checking only "it
ended up in the right state" would pass a run that duplicated an effect and
painted over it, which is the exact failure this engine exists to prevent.

The harness's own output is part of the deliverable. "The crash-simulation
harness passes" is invoked as a release gate from this phase forward, and it must
be unambiguous what that sentence claims.

Purpose: DUR-05, TEST-01, TEST-02 — and the project's stated release constraint.
Output: `internal/crashpoint`, the tier-1 matrix, and the tier-2 kill harness.
</objective>

<user_story>
**As a** team considering entflow for order and payment workflows,
**I want to** see a harness that kills a real worker at every step boundary and
proves no effect ever committed without its progress record,
**so that** I can trust the durability claim before I trust it with money.
</user_story>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| crash-point registry → production build | test-only instrumentation lives in a package the production claim path calls |
