<objective>
Give a run the three things it needs to be more than one step long: results that
survive the process that produced them, a live `self` entity re-read per step,
and honest terminal states.

Plan 02-02's tracer proved one step. This plan is what makes step two able to
read step one's output after a crash, what keeps `self` current rather than
stale, and what makes DUR-07's sentence — "after retries exhaust" — literally
true rather than aspirational.

Purpose: `entflow.Result[T]` was built in Phase 1 as an unexported seam
specifically so this phase could re-back it without changing a single call site.
Output: a JSON-backed result store, `entflow.WithSelfLoader`/`entflow.Self[T]`,
and the done / `failed:<step>` terminal transitions with a conservative DB-step
retry.
</objective>

<user_story>
**As a** developer writing a multi-step flow,
**I want to** read an earlier step's result and the current state of my entity
from inside a later step, exactly the same way whether or not a crash happened in
between,
**so that** I never have to reason about which of two code paths my flow took.
</user_story>

  <action>
    Make DUR-07's sentence true. A run whose steps all succeed reaches the done
    state with every result recorded; a run whose step fails after its retries
    are exhausted reaches the `failed:<step>` state with the error recorded.

    Write `worker/retry.go`. Declare `DefaultMaxAttempts` as 3 and a schedule
    that grows exponentially from 100 milliseconds to a 2 second ceiling with
    jitter applied, so a backing-off run neither spins the claim loop nor
    synchronizes with its siblings.

    Classify retryable errors **without importing a database driver** — this is
    the constraint that shapes the whole design, because a driver import would
    put a transport-adjacent module into entflow's production dependency graph
    and `TestNoTransportDeps` would go red. Three layers, in order: an
    `errors.As` against a locally-declared single-method interface exposing the
    SQLSTATE string, treating the serialization-failure and deadlock-detected
    codes as retryable (the widely-used Postgres driver's error type satisfies
    that interface without entflow naming it); `errors.Is` against the standard
    library's bad-connection sentinel from `database/sql/driver`, which is
    driver-agnostic and covers connection loss on all three dialects; and
    finally `Options.RetryableError`, the application-supplied hook, consulted
    when the built-ins do not match. That hook is how a MySQL deployment adds
    its own deadlock error numbers without entflow ever importing a MySQL
    driver. RESEARCH.md's Assumptions Log entry A4 notes this set is deliberately
    conservative rather than exhaustive; record in the doc comment that an
    unclassified transient error fails the run immediately, which is safe (it is
    inspectable and, from Phase 3, manually retryable) rather than
    silently-wrong, and that extending the set is additive.

    Every other error fails the run immediately without incrementing the attempt
    counter — retrying a business-logic error just burns the ceiling. Phase 1's
    declared `Retry(Backoff(...))` policy governs Activities and takes effect in
    Phase 3; it is deliberately not wired to DB steps here, and the doc comment
    must say so, so a reader does not assume a declared policy is silently
    ignored.

    In `worker/dbstep.go`, on a step error: classify it; if retryable and the
    attempt counter is below the ceiling, write an advance that increments
    `attempt` and sets `retry_after` to the scheduled time, leaving the state
    running and `current_step` unchanged so the same step is retried; otherwise
    write a failure that sets the state to the `failed:<step>` value for the
    failing step, records the error text in `last_error`, and sets
    `finished_at`. Both writes are guarded on the run still being in the running
    state at its recorded current step, and a guard miss must be handled — not
    ignored — by rolling back and treating the run as no longer ours, which is
    what prevents a completing or failing step from resurrecting a run that was
    cancelled while the step was in flight. The error text written to
    `last_error` comes from `StepError`'s rendered message, which names the step
    and the kind and never embeds the run's input bytes.

    Cover it in `worker/retry_test.go` against SQLite via `entclient`: a step
    returning a synthetic error carrying a retryable SQLSTATE is retried and the
    attempt counter increments and `retry_after` is set; the same step failing
    at the ceiling lands in the `failed:<step>` state with a non-empty
    `last_error` and `finished_at` set; a plain business error fails immediately
    with the attempt counter unchanged; a run reaching the done state has an
    empty `last_error`; an application-supplied `RetryableError` hook can make
    an otherwise-unclassified error retryable; and a guarded write against a run
    whose state was changed underneath it reports the guard miss rather than
    overwriting.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| step closure return value → persisted `results` column | application data crosses into durable storage and back out through `Result[T]` |
| driver error → entflow's retry classification | a third-party error value is inspected without entflow depending on the driver that produced it |
| step failure text → `last_error` column | an error message crosses into a column an operator will read |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-03 | Information Disclosure | `last_error` and the persisted `results` column | medium | mitigate | `last_error` is written from `StepError`'s rendered message, which names the step and kind and never embeds the run's input bytes — the same discipline `codec.go` established in Phase 1. `results` holds step return values, which are application data governed at row level by `Policy()` in plan 02-05; field-level redaction is explicitly out of scope and stated as a boundary rather than implied. |
| T-02-12 | Tampering | a completing or failing step resurrecting a cancelled run | high | mitigate | Every advance and failure write is guarded on the run still being in the running state at its recorded current step; a guard miss rolls the transaction back and abandons the claim rather than overwriting, and a test asserts the guard-miss path explicitly. |
| T-02-11 | Elevation of Privilege | a database driver import entering entflow's production graph via retry classification | high | mitigate | Classification uses a locally-declared single-method interface plus the standard library's bad-connection sentinel plus an application hook; an acceptance criterion asserts the worker's non-test dependency graph contains no Postgres driver. |
| T-02-13 | Denial of Service | a business-logic error consuming the retry budget and spinning the claim loop | low | accept | Only retryable driver errors increment the counter; everything else fails immediately, and `retry_after` gates claimability by time so a backing-off run cannot spin. The residual risk — an unclassified genuinely-transient error failing early — is documented as safe-and-additive rather than silently wrong. |
| T-02-SC | Tampering | Go module dependencies | high | mitigate | This plan adds **no** new modules by construction; the retry classification exists in its interface-assertion form precisely to avoid one. RESEARCH.md's `## Package Legitimacy Audit` shows no `[ASSUMED]`, `[SUS]` or `[SLOP]` package anywhere in the phase, so no blocking legitimacy checkpoint applies. |
</threat_model>
