<objective>
Fill the `ClaimStrategy` seam the tracer proved, with the real thing: a
`FOR UPDATE SKIP LOCKED` claim against a real Postgres, N independent claim
goroutines, and a conformance suite that proves — on all three dialects — that
two claimers never take the same row and that a rolled-back claim leaves the row
claimable.

Nothing about the shape proven in plan 02-02 changes. This is the expansion the
tracer was designed to admit: the strategy interface stays, the transaction
discipline stays, and the Postgres implementation drops in behind it.

Purpose: DUR-04's "multiple workers run concurrently with no coordination
service" stops being a design claim and becomes a test.
Output: the certified Postgres/MySQL strategy, real-Postgres test infrastructure,
and the D-38 conformance matrix.
</objective>

  <action>
    Turn `Worker.Run` into a pool of `Options.Concurrency` goroutines, each
    running its own claim cycle against its own transaction. Every goroutine
    calls the same claim-execute-advance function; nothing is shared between
    them but the engine, the stores, and the database. Do not batch: one claim
    transaction takes at most one run (D-31), because a batch would hold row
    locks across the execution of unrelated runs' steps.

    Each goroutine's iteration gets its own recover boundary around the
    transaction bookkeeping, mirroring `RunInTx`'s — separate from `runStep`'s
    per-closure recover, which already exists and must not be merged with it. A
    panic escaping one goroutine's iteration must roll that transaction back and
    let the goroutine continue rather than killing the worker process; a
    long-running worker that dies on one bad step is not durable.

    Honor the identity decision recorded in `docs/dialects.md`: no goroutine has
    an identity, no run is associated with a goroutine or a process beyond the
    lifetime of one claim transaction, and no state is kept in memory about
    which runs this worker has seen. If a data structure keyed by run ID appears
    anywhere in the worker, that is the anti-pattern — remove it.

    `Run` returns cleanly when its context is cancelled: stop starting new
    iterations and wait for in-flight ones. Full drain semantics and the poll
    jitter are plan 02-07's expansion; keep the ticker behavior from plan 02-02
    unchanged here so the two plans do not race on the same file.

    Add tests in `worker/worker_test.go`, against real Postgres via `pgtest`:
    start eight claimable runs and a worker with concurrency four, run to
    completion, and assert every run reached a terminal state exactly once and
    that the total count of step-effect mutations equals the number of runs —
    not more. Assert that two workers constructed against the same database and
    started simultaneously also produce exactly one terminal transition per run.
    Assert that a step closure that panics leaves its run claimable and the
    worker still running.

    Write one table-driven suite that runs the same two properties against every
    dialect in the matrix, so "the strategy is correct" is a claim the code
    makes about itself rather than a sentence in a document.

    Property one, no double claim: with K claimable runs and K concurrent claim
    transactions started together, the multiset of claimed IDs contains no
    duplicate, and every claimer either gets a distinct run or observes none.
    Property two, a rolled-back claim leaves the row claimable: claim a run,
    roll the transaction back, and assert a subsequent claim returns the same
    run.

    Run both properties against Postgres via `pgtest` and against SQLite via
    `entclient`. For SQLite, the transaction must be opened in immediate mode —
    the data-source name carries the transaction-lock parameter, which makes
    every transaction on that connection acquire its write lock at begin rather
    than at first write. That is what supplies the mutual exclusion the plain
    select needs, so property one holds there for a different reason than it
    holds on Postgres, and the test's own comment must say which mechanism it is
    relying on. Add the parameter to `pgtest`'s SQLite sibling or to a small

    acceptable in Phase 2 because SQLite is forced to a single worker anyway.
