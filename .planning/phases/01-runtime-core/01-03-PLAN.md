  <files>stepoptions.go, exec.go, step.go, flow.go, exec_test.go</files>
  <behavior>
    - Steps declared out of order but wired with `After` execute in dependency order; declaration order is the deterministic tie-break among independent steps.
    - A cycle in the `After` edges returns an error naming the participating steps, before any step executes.
    - An `After` edge naming a step that does not exist returns an error naming the missing step, before any step executes.
    - A flow containing an Activity or an Emit step returns an error satisfying `errors.Is(err, ErrRequiresDurableRun)` from `Exec`, and no step closure runs — asserted with an invocation counter that stays at zero.
    - `When(SelfWas("paid"))` on a status snapshot of `paid` runs the step; on a snapshot of `draft` it skips the step and records no result for it.
    - The snapshot is read once, inside the caller's transaction, before any step runs; a step that mutates the status does not change what a later `SelfWas` sees — asserted by a flow whose first step sets the status and whose second step is guarded by `SelfWas` on the ORIGINAL value.
    - A flow using `When(SelfWas(...))` with no `WithSelfStatus` option returns a declaration error naming the missing option.
    - A step closure that panics with an arbitrary value yields a `*StepError` whose `Step` and `Kind` match that step and whose `Stack` is non-empty; execution stops there.
    - A step body calling `Use[T]` with nothing provided yields a `*StepError` for which `errors.Is(err, ErrNotProvided)` is true — the panic value's error identity survives recovery.
    - A step body calling `Result[T](ctx, "cancel")` after step `cancel` succeeded receives that step's typed return value.
    - `RunInTx` commits on success and the mutation is readable through the non-transactional client afterwards.
    - `RunInTx` rolls back on any step error and the mutation is NOT readable afterwards — the all-or-nothing guarantee.
    - `RunInTx` rolls back and re-panics on a panic that escapes `Exec`, and its rollback error is joined into the returned error when both fail.
    - `Exec` never calls Commit or Rollback — asserted with a transaction double whose counters stay at zero.
  </behavior>
  <action>
Create `stepoptions.go` and move `Transition` into it from Plan 01's `flow.go`. Add `After(names ...string) StepOption` appending to the step's `dependsOn`, and `When(c Condition) StepOption` appending to the step's conditions.

Declare `Condition` as a DATA-ONLY struct — exported fields for the condition kind and the compared value, and no function-typed field anywhere. This matters beyond style: Plan 04's `meta` package renders conditions into `FlowMeta`, and CORE-11 requires every codegen-needed fact to be readable without evaluating anything. Add `SelfWas(status string) Condition` returning a `Condition` whose kind marks it as the entry-status predicate.

Add `WithSelfStatus[In, TX any](fn func(context.Context, TX, In) (string, error)) FlowOption` to `exec.go`. This is the explicit mechanism by which a flow declares HOW to read its owning entity's status, and it exists because entflow core can never name the application's generated entity type. It follows the same erasure pattern as the step constructors: the generic function captures the typed closure and stores a type-erased adapter on the flow config. Making the reader an explicit declared argument rather than something inferred from the `*Self` steps is required by ARCHITECTURE.md's Anti-Pattern 3 — record this as a derived design decision in the SUMMARY, since CONTEXT.md specifies D-10's semantics but not its mechanism.

Rewrite `exec.go`'s `Exec` to run these phases in order:

1. **Validate and order, before touching the transaction.** Resolve `After` edges into a topological order with declaration order as the tie-break. Return a descriptive error for an unknown referenced step or a cycle, naming the steps involved. Actionable validation errors before any execution is the UX rule PITFALLS.md calls for.
2. **Refuse durable-only flows.** If any step's kind is the activity kind or the emit kind, return an error wrapping `ErrRequiresDurableRun` naming the offending step, and execute nothing. D-13's rationale is that a naive in-line Activity path with no idempotency key and no persistence would create exactly the unsafe route this project exists to eliminate — the refusal must come before any partial execution, not after.
3. **Take the entry snapshot.** If the flow declares any `SelfWas` condition, invoke the `WithSelfStatus` reader once with the caller's transaction and the input, and store the returned status for the whole execution. If a `SelfWas` condition exists with no reader declared, return a declaration error naming the missing option. This once-at-entry read is precisely D-10's semantics, chosen so Phase 2 can replace the reader with a persisted column on the run row without changing what `SelfWas` means.
4. **Derive the execution context.** Attach a fresh result store using Plan 02's unexported seam. Do not construct a registry — propagate whatever the caller attached via `WithRegistry`; a step calling `Use[T]` on a registry-free context panics with `ErrNoRegistry`, which phase 5 below converts into a diagnosable `*StepError`.
5. **Execute each step in order.** Evaluate the step's conditions against the snapshot; a false condition skips the step and records no result. For each executed step, call its adapter inside a helper whose sole job is one `defer`/`recover` around one closure invocation. The recover site must be the innermost boundary around the user closure — never around the whole loop — so that a panic in one step cannot also swallow a bookkeeping bug in the executor's own step-to-step transition logic. On recover: if the recovered value is already an `error`, thread it through as the `%w`-wrapped cause so `errors.Is` still reaches sentinels like `ErrNotProvided`; otherwise format it into an error. In both cases capture `debug.Stack()` from `runtime/debug` into `StepError.Stack`. Converting the return path without discarding the diagnostic information is what keeps this from laundering a genuine runtime bug into an ordinary step failure.
6. **Record and abort.** On success, record the step's return value into the result store under the step's name so a later step's `Result[T]` finds it; record nothing for a `Check` step or a skipped step. On failure, return the `*StepError` immediately. `Exec` must not call Commit or Rollback — D-08 makes that the caller's responsibility, and Phase 2's worker depends on owning those calls.

Add `RunInTx[In any, T Tx](ctx context.Context, f *FlowOf[In], c TxOpener[T], in In) error` to `exec.go`, with `Tx` and `TxOpener[T]` declared as shown in the interfaces block. Follow ent's own documented pattern: open the transaction; install a deferred recover that rolls back and re-panics; call `Exec`; on a step error, roll back and, if the rollback ALSO fails, join the rollback error into the returned error rather than discarding either; on success, return the result of Commit. Keep this transaction-level recover strictly separate from the per-step recover of phase 5 — they protect different things (commit/rollback bookkeeping versus user closure panics) and collapsing them into one `defer` loses both jobs.

Write `exec_test.go` covering every behavior listed above. Several of these need doubles rather than the ent client: a transaction double implementing `Commit`/`Rollback` with counters proves `Exec` touches neither, while the commit-and-read-back and rollback-and-read-back assertions must run against the real fixture ent client so the all-or-nothing guarantee is proven at the database, not in memory.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Activity closure → database | The load-bearing boundary of this plan. An Activity must be structurally unable to write database state, so that an external call can never hold or use a transaction. |
| step closure → executor | Arbitrary user code runs here. It can panic, and in Phase 2 it will run inside a long-lived worker process. |
| flow declaration → executor | Declaration-time facts (ordering, conditions, transition claims) drive execution; a malformed graph must fail loudly before any effect occurs. |
