schema, and prove one flow end-to-end — declared on a schema via `Flows()`, executed against a

  <name>Task 1: Lock the published builder surface shape</name>
  <decision>
    Two coupled, one-way naming/shape decisions that define the API every future user schema is
    written against. Both are forced by Go language rules discovered during research and
    planning; neither is settled by CONTEXT.md.
  </decision>
  <context>
    **Why this cannot be deferred.** Go methods cannot declare their own type parameters
    (VERIFIED: `method must have no type parameters`, Go 1.25.1). The DB-step constructors need
    a `TX` type parameter (the closure receives the application's generated `*ent.Tx`, a type
    entflow core can never name) AND an `Ent` type parameter (the entity the closure returns) —
    both independent of `In`. `Activity` needs `Out` for `JSON[Out]`. Therefore NO step
    constructor can be a method on `*FlowOf[In]`, and the dot-chained syntax illustrated in
    entflow.md §3.1 cannot compile as written for any step kind.

    **Undo cost.** These identifiers and argument positions appear in every `Flows()` method in
    every consumer's schema files. Changing them after any external user imports the module is a
    breaking change to every consumer's source, not a refactor.

    Sub-decision A — constructor signature shape (all options use package-level generic
    functions; only the argument order differs). Sub-decision B — the `Flow` / `Flow[In]` naming
    collision: D-05 requires an interface named `entflow.Flow` returned from
    `Flows() []entflow.Flow`; D-07 requires `New[In]` to return `*Flow[In]`. One Go package
    cannot declare both. One of the two literal spellings must yield.
  </context>
  <options>
    <option id="A1-N1">
      <name>RECOMMENDED — A1 closure-third + N1 interface keeps the name `Flow`</name>
      <pros>
        A1: `UpdateSelf(f, "cancel", fn, Transition("cancelled"))` — closure in a fixed third
        position, variadic `StepOption` last. Idiomatic Go (variadic must be last). VERIFIED to
        type-infer `In`, `TX`, and `Ent` with zero explicit type arguments at the call site.
        Phase 5's AST parser walks a flat sequence of top-level `*ast.CallExpr` with the
        `*ast.FuncLit` at a fixed index — strictly simpler than an arbitrarily deep selector
        chain (RESEARCH.md schemast section).
        N1: schema files read `func (Order) Flows() []entflow.Flow`, an exact peer of
        `Hooks() []ent.Hook` and `Policy() ent.Policy`. That line is the most-read line of the
        whole design; the builder struct's name is nearly invisible because call sites use `:=`.
      </pros>
      <cons>
        A1: argument order differs from entflow.md §3.1's illustration, which shows options
        before the closure. N1: D-07's literal `*Flow[In]` becomes `*FlowOf[In]`.
      </cons>
    </option>
    <option id="A2-N1">

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application → entflow builder | The application supplies flow declarations and the input value; entflow treats both as caller-controlled but in-process (no network, no deserialization of remote bytes in this plan). |
| flow step → database | Every mutation must traverse the caller-supplied `*ent.Tx` so ent's entity hooks and privacy policies fire. A mutation issued through any other handle silently bypasses both. |
| developer toolchain → module dependency graph | Third-party Go modules enter the build here. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Elevation of Privilege | `exec.go` `Exec` / step `run` adapter | high | mitigate | `Exec` receives the transaction from the caller and passes that same handle to every DB step; it never constructs a client, opens a connection, or reaches for a package-level handle. The step closure's only database handle is the `TX` value entflow hands it, so ent's hook and privacy pipeline is on the only available path. Asserted by the end-to-end test, which reads the committed value back through the ordinary client. |
| T-01-02 | Tampering | `step.go` `run` adapter type assertion | medium | mitigate | The adapter uses the comma-ok form `tx.(TX)` and returns a descriptive error naming the step and both types. A bare panicking assertion here would convert a wiring mistake into an unrecovered process crash; Plan 03 adds the per-step recover, but the comma-ok form is required from the tracer onward. |
| T-01-03 | Information Disclosure | `internal/testdata/entclient` DSN | low | accept | The in-memory SQLite DSN contains no credentials and the database is destroyed at process exit. The helper is under a `testdata` path segment and cannot reach a non-test build. Accepted: there is no secret to leak. |
| T-01-SC | Tampering | Go module dependency graph (`entgo.io/ent`, `modernc.org/sqlite`, `stretchr/testify`) | high | mitigate | Per D-03, `entgo.io/ent` is pinned to the exact tag `v0.14.6` — never floating, never a pseudo-version. `go.sum` records module checksums and Go's default `GOSUMDB` verification validates them against the public checksum database on every fetch. CI sets `GOFLAGS: -mod=readonly` so a dependency cannot be silently added or upgraded by a build.
