## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Real import cycle between the fixture schema package and the generated ent package**

- **Found during:** Task 2, running `go vet ./...` after writing `exec_test.go`
- **Issue:** The plan's own research (01-RESEARCH.md, "ent's real runtime binding mechanism") assumed ent automatically routes schema-stitching through a separate cycle-breaking `ent/runtime` package whenever the schema imports generated types. In practice, ent's codegen decides this purely by counting `Hooks()`/`Policy()`/`Interceptors()` declared on the schema (`entc/gen/template/runtime.tmpl`) — it has no way to detect that a schema's custom `Flows()` method (unknown to ent's codegen) also imports generated types. Because the fixture `Order` schema declared no `Hooks()`/`Policy()`/`Interceptors()`, ent emitted the schema-stitching `init()` directly into the root `ent/runtime.go`, which imports `.../ent/schema` — and since `order_flows.go` (in package `schema`) must import the generated `ent`/`ent/order` packages for its `UpdateSelf` closure (`*ent.Tx`, `*ent.Order`, `order.StatusCancelled`), this created a genuine, unresolvable `schema -> ent -> schema` import cycle. `go build ./...` did not surface it (the affected packages live under an `internal/testdata` path segment the Go tool skips for wildcard matching), but `go vet ./...` and `go test ./...` did, because `exec_test.go` imports `.../ent/schema` by explicit path.
- **Fix:** Added a genuine, effect-free passthrough `Hooks() []ent.Hook` method to the fixture `Order` schema (`internal/testdata/ent/schema/order.go`) — a single hook that returns `next` unchanged. This gives ent's codegen a nonzero hook count, which triggers its existing cyclic-import-avoidance split: the schema-stitching logic and the import of `.../ent/schema` move into the separate `internal/testdata/ent/runtime` package, and root `internal/testdata/ent/runtime.go` becomes a one-line pointer comment with no schema import. Also added a blank import of `.../ent/runtime` to `internal/testdata/entclient/client.go` so the hook actually registers into the generated `order.Hooks` array at init time (otherwise `order_update.go`'s `withHooks` call would invoke a nil function).
- **Files modified:** `internal/testdata/ent/schema/order.go`, `internal/testdata/entclient/client.go` (both already `files_modified` scope per the plan; no new files added), plus the regenerated `internal/testdata/ent/runtime.go` and `internal/testdata/ent/runtime/runtime.go`.
- **Verification:** `go build ./...`, `go vet ./...`, and `go test ./... -race` all exit 0 after the fix; `internal/testdata/ent/runtime.go` confirmed to contain only a pointer comment (no schema import).
- **Committed in:** `f9c49bd` (Task 2 commit — this fix was folded into the same tracer commit since it was discovered mid-task, before the tracer's own commit)

**Total deviations:** 1 auto-fixed (1 blocking — Rule 3)
**Impact on plan:** Necessary for `go vet`/`go test` to pass at all; no scope creep beyond the single no-op hook and its blank-import registration. This is a genuinely new finding not covered by Phase 1's research — worth flagging for Phase 5/6 planning, since entflow's own future entc extension will need to either (a) always emit at least one real hook (e.g., the SM-02 transitions-enforcing hook, which lands in Phase 6 anyway and would obviate this workaround), or (b) special-case its own generated schema files to avoid depending on this same lever.
