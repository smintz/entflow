## CRITICAL FINDING: entflow.md §3.1's illustrated API does not compile as written

**The problem:** Go methods cannot declare their own type parameters — only the receiver's
existing type parameters are available inside a method body/signature. `entflow.md` §3.1 shows
`Activity(...)` chained fluently as if it were a method on `*Flow[In]`:

```go
entflow.New[*orderv1.CancelOrderRequest]("CancelOrder").
    UpdateSelf("cancel", ..., func(ctx, tx, in) (*ent.Order, error) {...}),
    Activity("refund", ...,
        func(ctx context.Context, o *ent.Order, att entflow.Attempt) (entflow.JSON[RefundResult], error) {...}),
    Emit("order.cancelled", entflow.After("cancel")),
```

`Activity`'s closure return type is `entflow.JSON[Out]` where `Out` (here `RefundResult`) is
**independent of `In`** (`*orderv1.CancelOrderRequest`). For the compiler to check this closure's
signature, `Out` must be a type parameter in scope at the point `Activity` is declared. If
`Activity` is a method on `*Flow[In]`, `Out` is NOT available — `Flow[In]`'s only type parameter
is `In` (locked by D-07). Declaring a second type parameter on the method is a compile error.

**VERIFIED reproduction** (`go build` output, Go 1.25.1, this session):
```go
func (f *Flow[In]) Activity[Out any](name string, fn func(in In, att Attempt) (JSON[Out], error)) *Flow[In] {
	return f
}
```
```
./main.go:20:28: syntax error: method must have no type parameters
```

**The fix — package-level generic function, not a method.** Moving `Out` (and `In`) to a
package-level function's own type-parameter list works and type-infers cleanly from the closure
literal with no explicit instantiation required:

```go
func Activity[In, Out any](f *Flow[In], name string, fn func(in In, att Attempt) (JSON[Out], error)) *Flow[In] {
	return f
}
// call site — Out=RefundResult and In=string both inferred, no explicit [In, Out]:
Activity(f, "refund", func(in string, att Attempt) (JSON[RefundResult], error) {
    return NewJSON(RefundResult{RefundID: "re_123"}), nil
})
```
**VERIFIED**: this compiles and runs (`go build && go run`, this session).

**Consequence for the planner:** the design doc's dot-chained fluent syntax
(`New[...]("X").UpdateSelf(...).Activity(...).Emit(...)`) cannot be preserved *exactly as
illustrated* for any step kind whose closure needs a type parameter independent of `In` (Activity
is the clear case, via `JSON[Out]`). The corrected shape breaks the chain into either:
- sequential statements mutating the same `*Flow[In]` pointer (`f := New[In](...); UpdateSelf(f, ...); Activity(f, ...)`), or
- package-level functions that still return `*Flow[In]` so *method*-only steps (ones with no
  extra type param) can keep chaining, with function-style calls interspersed for Activity/Emit.

D-13 already says "Activity and Emit are declarable... their builder methods" — the word
"methods" needs correcting to "constructors" in planning language; Phase 1 must decide (Claude's
Discretion, internal representation) whether *all* step kinds become package-level functions for
API consistency, or only the ones that strictly require it. This is the single highest-value
finding of this research pass — the planner must design the builder surface around this
constraint before writing any task that assumes the literal §3.1 syntax compiles.

## ent's real runtime binding mechanism for Hooks()/Policy() [VERIFIED: generated locally]

Generated a real minimal ent v0.14.6 project (schema `Order{status string}` + a `Hooks()` method
whose closure references the generated `*ent.OrderMutation` type, forcing the cyclic-import case)
and read the actual output, this session.

**Two generation modes, chosen automatically by ent based on cyclic-import risk:**

1. **No cyclic risk** (schema methods don't reference generated types): the stitching logic is
   emitted directly into the root generated package, `ent/runtime.go`:
   ```go
   // Code generated by ent, DO NOT EDIT.
   package ent
   func init() {
   }
   ```
   and `ent/runtime/runtime.go` is just a version stamp (`const Version = "v0.14.6"`).

2. **Cyclic risk** (schema's `Hooks()`/`Policy()` closures reference generated types, e.g.
   `*gen.OrderMutation` — entflow's `Flows()` will always be in this bucket, since step closures
   reference `*ent.Tx`, `*ent.Order`, etc.): `ent/runtime.go` becomes a one-line pointer comment,
   and the REAL wiring moves to the separate `ent/runtime` package:
   ```go
   // ent/runtime.go
   package ent
   // The schema-stitching logic is generated in entgen/ent/runtime/runtime.go

   // ent/runtime/runtime.go
   package runtime
   import (
       "entgen/ent/order"
       "entgen/ent/schema"
   )
   func init() {
       orderHooks := schema.Order{}.Hooks()
       order.Hooks[0] = orderHooks[0]
   }
   const ( Version = "v0.14.6" ... )
   ```
   `entgen/ent/order/order.go` declares the package-level var ent's generated mutation code reads
   from: `var Hooks [1]ent.Hook` (verified via `grep -n "Hooks" ent/order/order.go` → `43: Hooks [1]ent.Hook`).

**Mechanism, precisely:** the separate `ent/runtime` package imports BOTH the schema package
(`.../ent/schema`) and the generated leaf package (`.../ent/order`), calls
`schema.Order{}.Hooks()` to obtain the closures (this is the only place in the generated code
that ever calls the schema method), and assigns them **by position** into the generated
package's exported `Hooks [N]ent.Hook` array. `order_update.go` reads `_u.hooks` at
`Save`-time via `withHooks(ctx, _u.sqlSave, _u.mutation, _u.hooks)` — confirmed by
`grep -n "Hooks\|runtime" ent/order_update.go`.

**Why this breaks the cycle:** the schema package can freely import the generated package
(`*ent.OrderMutation` etc.) because `ent/runtime` — not the schema package, and not the root
`ent` package — is the thing that imports the schema package. The generated root `ent` package
never imports `ent/schema`, so there's no cycle: `ent/schema` → `ent` (one direction),
`ent/runtime` → `ent/schema` AND `ent/runtime` → `ent` (safe, since `ent` doesn't import back).

**Application-level requirement:** the app must blank-import the runtime package
(`import _ "entgen/ent/runtime"`) for `init()` to run and the hooks to actually be wired —
confirmed against `entgo.io/docs/hooks/` [CITED: entgo.io/docs/hooks/], which states this
explicitly and also documents the two-pass bootstrap: comment out hooks referencing generated
types → `go generate` → uncomment → `go generate` again.

**Direct implication for `Flows()` (D-05/D-06):** Phase 1's `entflow.FlowsOf(schema any) []Flow`
helper is the *hand-written* substitute for what `ent/runtime`'s generated `init()` does
automatically in the codegen'd future (Phase 5/6) — it must call `Flows()` on each registered
schema value and hand the returned builder DATA to the registry, exactly mirroring
`schema.Order{}.Hooks()` → `order.Hooks[0] = ...`. Phase 1 has no generated `ent/runtime`
package to extend (no codegen yet), so `FlowsOf` + explicit `main.go`/test registration IS the
Phase-1-honest equivalent of what a future `ent/runtime.go` would do automatically — this is
exactly the "explicit registration, not reflection" framing D-06 already locks in, now backed by
the concrete mechanism it mirrors.

## Tx discipline for the hand-written executor [CITED: entgo.io/docs/transactions/]

`client.Tx(ctx)` returns `(*ent.Tx, error)`. Typed builders come off the tx via the same
per-entity accessor pattern as the client: `tx.Order.UpdateOneID(...)`. Canonical
commit/rollback/panic pattern from ent's own docs:

```go
tx, err := client.Tx(ctx)
if err != nil {
    return fmt.Errorf("starting a transaction: %w", err)
}
defer func() {
    if v := recover(); v != nil {
        tx.Rollback()
        panic(v)
    }
}()
// ... mutations via tx.Order.Create()... / tx.Order.UpdateOneID()...
if err := doStuff(tx); err != nil {
    if rerr := tx.Rollback(); rerr != nil {
        err = fmt.Errorf("%w: rolling back transaction: %v", err, rerr)
    }
    return err
}
return tx.Commit()
```

**`tx.Client()`** returns a `*ent.Client` scoped to the transaction — every generated builder
method obtained through it participates in the same tx, and existing code written against
`*ent.Client` can be reused unmodified. **Hooks and privacy policies fire normally** on tx-scoped
mutations (this is the mechanism D-09/CORE-03's "entity hooks and privacy policies fire on every
mutation" claim rests on — it is not special-cased for transactions, it is the same mutation
pipeline). One documented caveat: after `Commit()`, entities loaded through the tx need
`Unwrap()` before querying edges through the non-tx client — not directly relevant to Phase 1
(no post-commit edge traversal in the executor) but worth flagging for anyone writing
`internal/testdata/ent` test helpers that re-query after `Exec` returns.

**Direct implications for D-08 (`Exec`/`RunInTx`):**
- `Exec(ctx, tx *ent.Tx, in In)` is the primitive: it must NOT call `tx.Commit()` or
  `tx.Rollback()` itself — those are the caller's responsibility per D-08's own wording ("neither
  opens nor commits"). Internally, each DB step's closure receives `tx` directly (or `tx.Client()`
  if a helper prefers `*ent.Client`-shaped code) — no new transaction is opened per step in Phase
  1 (that's a Phase 2 worker concern where each step gets a fresh claim/tx cycle; Phase 1 is a
  single caller-supplied tx end to end, matching the Ecto.Multi baseline).
- `RunInTx(ctx, client *ent.Client, in In)` is exactly the sugar shown in ent's own docs pattern
  above: open tx, defer the panic-rollback, call `Exec(ctx, tx, in)`, roll back on step error,
  commit on success. The `recover()`-and-repanic idiom belongs at this layer (or one layer up in
  `Exec`'s own per-step recovery per D-16) — recommend keeping the tx-level recover in
  `RunInTx` (protects `Commit`/`Rollback` bookkeeping) as a SEPARATE recover from the per-step
  recover D-16 requires around each step closure invocation (protects DI/`Use[T]` panics from
  killing the whole executor ungracefully) — two different recover sites, two different jobs, do
  not collapse them into one `defer`.
- D-09's `*entflow.StepError` wrapping "the underlying cause" should wrap ent's own error types
  transparently (`errors.Is`/`errors.As` must still reach through to e.g. `*ent.NotFoundError` or
  a validation error from a hook) — `fmt.Errorf("%w: ...", cause)` composition, not a bespoke
  error struct that swallows the original.

## Custom schema.Annotation: defining SM-01's Transitions and reading it back

**The interface contract** [VERIFIED: `/Users/smintz/go/pkg/mod/entgo.io/ent@v0.14.6/schema/schema.go:12-15`, read this session]:
```go
type Annotation interface {
	// Name defines the name of the annotation to be retrieved by the codegen.
	Name() string
}
```
That is the entire contract — one method, returning a stable string key. `entflow.Transitions(...)`
just needs a concrete type implementing `Name() string` (e.g. returning `"Transitions"` or a
namespaced `"EntflowTransitions"` to avoid collisions with other extensions' annotations on the
same field).

**Attachment** [VERIFIED: `/Users/smintz/go/pkg/mod/entgo.io/ent@v0.14.6/schema/field/field.go`,
grep confirmed `func (b *enumBuilder) Annotations(annotations ...schema.Annotation) *enumBuilder`
at line 1133]: every field builder (including `enumBuilder`, the one `field.Enum(...)` returns)
exposes a variadic `.Annotations(...)` method accepting `schema.Annotation` values. Matches the
design doc's `field.Enum("status").Values(...).Annotations(entflow.Transitions(map[...]{...}))`
exactly as illustrated — no compile-shape problem here (unlike Activity/§3.1, `Annotations` takes
no extra type parameter, it's an ordinary variadic interface-slice method).

**Reading it back — the load-bearing part for Phase 6, and Phase 1's obligation to make possible
now.** [VERIFIED: `entc/gen/type.go`, read this session] `gen.Field`/`gen.Type` store annotations
as `Annotations map[string]any` (`entc/gen/graph.go:141`, confirmed `type Annotations map[string]any`
and `func (a *Annotations) Set(k string, v any)`), keyed by each annotation's own `Name()` string
at graph-build time (`entc/gen/type.go:219`: `Annotations: schema.Annotations`). ent's own internal
code demonstrates the canonical decode pattern for reading a typed annotation back out of that
map — `entc/gen/type.go:1091-1104`:
```go
func (t Type) sqlComment() string {
	ant := &entschema.CommentAnnotation{}
	if t.Annotations == nil || t.Annotations[ant.Name()] == nil {
		return ""
	}
	if b, err := json.Marshal(t.Annotations[ant.Name()]); err == nil {
		_ = json.Unmarshal(b, &ant)
	}
	return ant.Text
}
```
The pattern: look up `t.Annotations[ant.Name()]` (present as a loosely-typed `any`, decoded from
JSON at graph-load time since annotations round-trip through the loader as JSON), `json.Marshal`
it back to bytes, then `json.Unmarshal` into a zero-value instance of the concrete annotation
struct. This is the SAME mechanism entgql/entproto use for their own custom annotations — it is
ent's sanctioned, universal annotation-decode idiom, not something specific to built-in
annotations.

**Consequence for SM-01 / D-14:** `entflow.Transitions(map[string][]string{...})` must be a
JSON-marshalable struct (a bare `map[string][]string` wrapped in a named type with a `Name()`
method works fine — maps round-trip through `encoding/json` cleanly). Phase 1's obligation per
D-14 ("Phase 1 must make the annotation readable from the schema graph so Phase 6 has something
to validate against") is satisfied simply by: (a) defining the type with `Name() string`, (b)
writing a **Phase-1-owned accessor** — e.g. `entflow.TransitionsOf(field *gen.Field) (map[string][]string, bool)`
or equivalent — that performs exactly the `Annotations[Name()]` → `json.Marshal` → `json.Unmarshal`
round-trip above, so Phase 6 doesn't reinvent it. This accessor operates on `gen.Graph`/`gen.Field`
types from `entgo.io/ent/entc/gen` — Phase 1 does not need to import `entc/gen` for the runtime
library itself (that would violate the "root package has zero codegen dependency" structure rule
in `research/ARCHITECTURE.md`), so this accessor should live in a place that already depends on
`entc/gen` (i.e., deferred to whichever package first needs to read it — likely `entc/validate/`
in Phase 6, not `entflow` core) OR Phase 1 ships only the annotation TYPE + its `Name()` method in
core, and defers the `gen.Field`-reading accessor's implementation to Phase 6 while proving *in a
unit test* that a `gen.Graph` loaded from the fixture schema contains the expected
`Annotations["Transitions"]` entry decodable via the pattern above — satisfying D-14's "readable"
requirement without prematurely importing `entc/gen` into the root module. Recommend the latter:
write the round-trip-readability test now, ship the accessor function in Phase 6 alongside its
first real caller.

## Context-carried generic accessors: Result[T] and Use[T] [VERIFIED: compiled+ran locally, Go 1.25.1]

Both `entflow.Use[T](ctx)` (D-16, DI) and `entflow.Result[T](ctx, "step")` (D-11, cross-step
results) are variants of the same idiom: **one** value stored in `context.Context` via an
unexported key type, internally holding a `map` keyed by `reflect.Type` (`Use`) or by step-name
string (`Result`), with the generic wrapper doing a type assertion at the read site. This avoids
the documented Go anti-pattern of calling `context.WithValue` once per concrete type — store a
single registry/store value in context, do typed lookups inside it.

**DI registry (`Provide`/`Use`/`TryUse`) — VERIFIED compiling and running this session:**
```go
type registryKey struct{}
type Registry struct {
	mu    sync.RWMutex
	items map[reflect.Type]any
}
func NewRegistry() *Registry { return &Registry{items: map[reflect.Type]any{}} }
func Provide[T any](r *Registry, v T) {
	r.mu.Lock(); defer r.mu.Unlock()
	r.items[reflect.TypeFor[T]()] = v
}
func WithRegistry(ctx context.Context, r *Registry) context.Context {
	return context.WithValue(ctx, registryKey{}, r)
}
func TryUse[T any](ctx context.Context) (T, error) {
	var zero T
	r, ok := ctx.Value(registryKey{}).(*Registry)
	if !ok { return zero, ErrNoRegistry } // distinct sentinel
	r.mu.RLock(); defer r.mu.RUnlock()
	v, ok := r.items[reflect.TypeFor[T]()]
	if !ok { return zero, fmt.Errorf("%w: %T", ErrNotProvided, zero) } // distinct sentinel
	return v.(T), nil
}
func Use[T any](ctx context.Context) T {
	v, err := TryUse[T](ctx)
	if err != nil { panic(err) }
	return v
}
```
`reflect.TypeFor[T]()` is the Go 1.22+ stdlib generic helper (avoids the old
`reflect.TypeOf((*T)(nil)).Elem()` boilerplate) — confirmed available and correct under the
project's Go 1.25 target. This satisfies D-16 exactly: `Use[T]` panics on missing provider,
`TryUse[T]` returns the error for callers who want it, and the panic is a plain Go error value
(not an untyped string) so the executor's per-step `recover()` (also D-16) can `errors.As` it
into `*entflow.StepError` cleanly rather than stringly-matching a panic message.

**Result[T] follows the identical shape**, swapping the key type (`reflect.Type` → step-name
`string`) and requiring TWO distinct sentinel errors per D-11 ("distinct sentinel errors for
unknown-step and for type-mismatch"):
```go
type resultsKey struct{}
type resultStore struct {
	mu      sync.Mutex
	results map[string]any
}
func Result[T any](ctx context.Context, step string) (T, error) {
	var zero T
	rs, ok := ctx.Value(resultsKey{}).(*resultStore)
	if !ok { return zero, ErrNoResultStore }
	rs.mu.Lock(); defer rs.mu.Unlock()
	v, ok := rs.results[step]
	if !ok { return zero, fmt.Errorf("%w: %q", ErrUnknownStep, step) }
	typed, ok := v.(T)
	if !ok { return zero, fmt.Errorf("%w: step %q produced %T, want %T", ErrResultTypeMismatch, step, v, zero) }
	return typed, nil
}
```
The `v.(T)` comma-ok form (never the panicking bare assertion) is what turns PITFALLS.md's
Pitfall 6 ("stringly-typed decay into runtime panics") into a returned, `errors.Is`-checkable
error instead of an actual panic — Phase 1 should treat a bare `.(T)` assertion anywhere in this
path as a code-review-blocking mistake, since it silently reintroduces the exact failure mode
D-11 exists to prevent. [ASSUMED: the general context-registry pattern above is well-established
Go idiom, not sourced from a single authoritative doc this session, but the DI-registry variant
was compiled and executed successfully in this session's scratch environment, which is stronger
than a training-data claim.]

## Step-boundary panic recovery (D-16) — converting panics to *entflow.StepError without swallowing bugs

D-16 requires the executor to recover panics "at every step boundary" (this covers `Use[T]`'s
panic on missing provider, but also any other panic a user's step closure raises — a nil-pointer
bug, an out-of-range index, etc.) and convert them into a `*entflow.StepError`, so a DI wiring
mistake fails the run cleanly rather than (in Phase 2+) killing a long-running worker process.
The risk in any blanket `recover()` is masking a genuine programming bug as "just another step
failure" and hiding it from crash/monitoring visibility — the mitigation is to preserve the
original panic value's type and a stack trace inside the resulting error, not just stringify it:

```go
func runStep(ctx context.Context, name string, kind StepKind, fn func() error) (err error) {
	defer func() {
		if r := recover(); r != nil {
			var cause error
			if e, ok := r.(error); ok {
				cause = e // preserves errors.Is/As-ability, e.g. our own ErrNotProvided from Use[T]
			} else {
				cause = fmt.Errorf("panic: %v", r)
			}
			err = &StepError{
				Step: name, Kind: kind,
				Err:   cause,
				Stack: debug.Stack(), // captured at panic site, not lost
			}
		}
	}()
	return fn()
}
```
Key points: (1) `recover()` happens exactly once per step invocation, at the innermost boundary
around the user closure call — not around the whole `Exec`/`RunInTx` loop, so a panic in step 3
doesn't also swallow bookkeeping bugs in the executor's own step-3-to-4 transition logic; (2) if
the recovered value is already an `error` (as `Use[T]`'s panic value is, by construction above),
it's threaded through as the error's `%w`-wrapped cause so `errors.Is(err, entflow.ErrNotProvided)`
still works after recovery — this is why `Use[T]`'s panic value should be an `error`, never a bare
string, matching the recommendation in the Result[T]/Use[T] section; (3) `debug.Stack()`
(`runtime/debug`) captured inside the recover keeps the original panic's call site visible in
logs/observability even though the panic itself has been converted to a normal error return —
this is the concrete way to avoid "swallowing a runtime bug" while still satisfying D-16's
"convert to StepError" requirement: convert the *return path*, not the *diagnostic information*.
[ASSUMED: standard Go recover/error-wrapping idiom, not sourced from an external authority this
session — low risk, this is well-trodden Go practice, not something specific to ent or entflow.]

## In-memory SQLite ent client wiring with modernc.org/sqlite (D-21)

**Driver name — VERIFIED via `pkg.go.dev/modernc.org/sqlite` docs fetch this session:**
`modernc.org/sqlite` registers itself with `database/sql` under the driver name **`"sqlite"`**
(not `"sqlite3"` — that name belongs to the CGo `mattn/go-sqlite3` driver most ent examples on
the web use). Getting this wrong is the single most likely copy-paste mistake: code copied from
a typical ent quickstart (`ent.Open(dialect.SQLite, "file:ent?...")` — dialect.SQLite string
constant is `"sqlite3"` internally in some ent examples/wrappers, but the actual `sql.Open` driver
name argument must match whatever the imported driver registered) will silently fail to find the
driver if the import is `modernc.org/sqlite` but the driver name string used is `"sqlite3"`.

**DSN format** [CITED: pkg.go.dev/modernc.org/sqlite]: modernc's driver supports both a bare
filename and a `file:` URI with query parameters. Confirmed supported parameter aliases include
`_foreign_keys` / `_fk` (values `0/1`, `false/true`, `no/yes`, `off/on`) — i.e. the common ent
quickstart DSN `"file:ent?mode=memory&cache=shared&_fk=1"` should work verbatim against
modernc.org/sqlite's own DSN parser, contrary to an older community claim (the `sqlite3ent/sqlite3`
bridge package's README) that plain modernc.org/sqlite can't parse `_fk=1` — that claim appears to
predate modernc adding the `_fk` alias for `_foreign_keys`. **Recommendation:** try plain
`modernc.org/sqlite` with `_fk=1` first (matches D-21's stated dependency exactly, no extra
bridge package); only reach for `sqlite3ent/sqlite3` if a Phase-1 smoke test proves the alias
doesn't resolve correctly against the pinned modernc version. [MEDIUM confidence: cross-checked
pkg.go.dev docs (more current/authoritative than the bridge repo's README) but not proven against
ent's own connection-opening code path in this session — verify with one real `sql.Open` +

## schemast's read surface (only as far as D-20's golden snapshot needs)

Phase 1 does not implement AST extraction (D-20 explicitly reserves that for Phase 5), but D-20
requires Phase 1 to snapshot the builder-chain **call shapes** (which functions/methods are
called, in what order, with what argument kinds) so Phase 5's AST parser has a concrete contract
to match against. Per `research/STACK.md` and `research/ARCHITECTURE.md` (already HIGH-confidence,
source-verified in prior project research — reused here, not re-verified this session)
[CITED: research/STACK.md, research/ARCHITECTURE.md]: `entgo.io/contrib/schemast` operates on the
Go **AST** of the `schema/` package (`schemast.Load(dir)` → mutate → `ctx.Print(dir)`), not on
compiled/reflected values — meaning it CAN see call expressions, string/int literals, and
selector chains textually, but CANNOT see anything that only exists at runtime (closure bodies,
values computed by function calls it doesn't specifically model, results of type inference). Given
this session's Activity/generics finding, the practical consequence for D-20's snapshot is:
**the golden snapshot must record call shapes as flat, ordered invocations** (e.g.
`New[T]("CancelOrder")`, `UpdateSelf(f, "cancel", Transition("cancelled"), <closure>)`,
`Activity(f, "refund", When(...), Retry(...), <closure>)`) rather than as a fluent dot-chain,
because — as established above — the real API will not always BE a dot-chain. This is good news
for Phase 5's AST work: `go/ast` walking a sequence of top-level `*ast.CallExpr` statements
(package-level function calls) is simpler and more robust than walking an arbitrarily deep
`*ast.SelectorExpr`/`*ast.CallExpr` chain, so the generics-forced API shape is, incidentally, the
easier one for `schemast`/`go/ast` to parse later — Phase 1's snapshot should capture this
explicitly as a documented finding for Phase 5's planner, not just as an implementation detail.
